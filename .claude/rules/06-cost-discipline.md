## 零、任务分级与编排（T0~T3）

**按任务分级决定编排深度**：禁止"一刀切"审批式多人协作，也禁止**该多 Agent 时**的 solo 串行。
分级依据：复杂度、领域跨度、可逆性、成本、合规（竞赛/论文）。

**多 Agent 的真实代价不在底盘，在轮数。** §五实测：同会话「子 Agent 支出 / 主链支出」中位 **0.56×**
（17 个会话，0.02×–3.69×）；早先"多 Agent ≈ 单 Agent 的 15× token"的估计**未被实测支持**。
多 Agent 的成本体现在**轮数 × 每轮上下文**（§五 硬约束 3），故 T1 这类「单一领域、可逆、中低成本」
任务**默认单 Agent 串行**——它正是最不该用多 Agent 的那类。多 Agent 只花在该花的地方：
跨领域并行、确需上下文隔离、或 T2/T3 的强制独立审查。

| 级别 | 判定（分级依据即触发条件；排除即 T0/T1） | 编排方式 | 确认点 |
|------|------|---------|--------|
| **T0 单步** | 单步查询、简单文件读写、明确指定步骤 ≤2 | 直接执行，不触发秘书 | 无 |
| **T1 常规** | 单一领域、步骤 ≥3、可逆、中低成本 | **默认单 Agent 串行**；仅当跨领域 / 需并行 / 不可逆时才升级为多 Agent | 无硬停；执行后汇报 |
| **T2 复杂** | 跨领域 / 不可逆（含采购数据、长时间计算等**不可逆高成本**）/ 重计算或大数据量 / 需多轮实验 / 论文报告撰写 / 架构重构 | 秘书分解 + **一次**确认（仅确认无合理默认值且影响交付的决策项） | 分解确认（合并审议点） |
| **T3 竞赛/论文** | MCM / Kaggle / 期刊论文流水线 | 走专用赛道规则（`04-mcm-track.md` / `03-kaggle-track.md` / `09-journal-track.md`） | 收敛到真决策点（选题/模型路线/终稿） |

**默认值原则**：分解方案必须为每个决策项给出推荐默认值。用户未在合理时间内回复 → 按方案声明默认值推进
并持续汇报，用户随时可插入指令修正，不无限等待。

**判定实例**："帮我做国赛C题" → T3；"用这份数据建个预测模型" → T1/T2（视数据量与可逆性）；
"统计这个文件夹有几个文件" → T0。

### 编排流程（三阶段）

**阶段 0 — 秘书分解（T2/T3 强制，T1 可选）。T2/T3 不得跳过。**
调用 `agents/secretary.md`（T0 不介入）。分解方案的四项必备内容——子任务列表 + Agent 分派计划 +
并行标注、每个决策项的**推荐默认值**、至少 1 个独立 critic、输出格式模板——**唯一源是 `agents/secretary.md`**，
本文件不复述。**T2/T3 在秘书分解确认前进入实现阶段视为违规。**

**阶段 1 — 用户确认（T2；T3 收敛到真决策点）。**
"可以" → 进入阶段 2；"XX 需要调整" → 修订对应决策项后**重新确认该次方案**（不回退全部）；
"不需要多 Agent，直接做" → 降级为最小编排（**至少保留 1 个 critic**）；超时未回复 → 按默认值推进。

**阶段 2 — 执行（Orchestrator 接管）。** 无依赖子任务 → `parallel()`；有依赖 → `pipeline()`。
每完成一个阶段汇总结果并写共享记忆。上下文饱和度口径与切割条件见 `agents/orchestrator.md` §3。
**阶段 3 — 审查。** 独立 critic 检查 → 不通过则 fixer 修复 → 回到 critic。轮次封顶与触顶升级出口见 §二。

### 禁止行为

- 一次性写 500+ 行代码到一个文件（模块化拆分由任务结构驱动，不设 200 行之类的二次阈值）
- 自己写代码 → 自己运行 → 自己画图 → 自己写报告（**T2/T3** 禁止全流程单人；
  T1 单 Agent 串行**是默认**，不受此条约束）
- T2/T3 跳过秘书分解直接开始探查 / 写代码 / 生成图表；用"太复杂不好拆"或"我先看看情况"绕过本规则
- critic 输出的问题自己手动修改（应由 fixer Agent 修改）

### 开工前自查（3 问）

1. 该任务属于 T0~T3 哪一级？→ 先分级
2. T2/T3：是否已输出分解方案并经确认？→ 否则暂停；T1 无需确认、无需分解，按默认值直接执行
3. 当前工作**值得**拆成 ≥2 个 Agent 吗？→ T1 默认**不拆**；仅当跨领域 / 可并行 / 确需上下文隔离时才拆；
   T2/T3 按规则拆，不适用此门槛

> 秘书门禁**无**机械保证——见 §三 注。

## 一、检验分层（L1 / L2 / L3）

**前提：不信任 AI 的口头成功报告。** 交付前必须**真实运行**验证——代码改完实际跑、结果生成后查数值
合理性（极端值 / 缺失 / 符号方向）、复现包在干净环境测一键运行。未通过 → 标 **FAIL**，**阻断后续流程**，
先修复；通过 → 标 **PASS**。

复核不是越多越好。**按层级决定做不做**，避免在已验证结论上反复自证。

| 层 | 内容 | 默认 | 成本 |
|----|------|------|------|
| **L1 正确性** | 退出码 0 + 断言全过；交付表结构/表头/行序同模板；数值落物理边界；每个数字回溯到**一个**结果字段（单次核对）；章节自检 FAIL 0；禁用词 | **必做** | 低 |
| **L2 稳健性** | 灵敏度 / 情景 / 退化极限——仅当存在值得检验的不确定参数**且结论可能翻转**时做；**一次运行**即可，不追求网格穷举 | **按需** | 中 |
| **L3 复核** | 多臂并行对抗复核、逐字节可逆证明 / md5 反代回写、全集排序位次复核、重复重跑比对 | **默认不做** | 高 |

**L3 的唯一触发条件**：L1 出现 FAIL，或用户对某个**已交付**数值提出质疑。
触发时须写明**是哪条判据、哪个数值、为什么存疑**，不得泛化重跑。

**禁止**：任何 Agent **不得自发启动 L3 复核**。判据全部 PASS 后再补做对抗臂、逐字节还原、
全集排序多轮扫描、重跑比对，均属违规——这些检查在结论已确证后不产生新信息，只消耗预算。
数值溯源一律**单次核对**（打开产出该数字的那一行看字段名），不做多轮全集排序复核。

## 二、产出纪律

| 规则 | 内容 |
|------|------|
| **禁止全文快照** | 任何环节**不得**把整篇交付物或整个 `sections/` 复制进归档目录。版本历史交给 git；确需留底时只备份**被修改的那一个文件**，注明轮次与理由 |
| **状态记录上限** | 状态记录用**追加行**格式，单条 ≤ 200 字，**只追加不重写全文**；禁止把叙述性长文写进状态记录 |
| **禁止独立跟踪文档** | 不新建长篇状态跟踪文档（如 `README.md` 式进度报告）；跟踪信息一律进状态记录 |
| **实验日志** | 严格**一行一实验、列固定**；禁止在单元格内写报告。叙述性内容另存短文件，每实验一个 |
| **审查轮次封顶** | **全局唯一次数口径**：同一交付物/节点复核**上限 3 轮**（含首轮全文），每轮**只复核 FAIL 项**，禁止对已 PASS 项重复复核。**终稿自收为 1 轮**——一次性输出全表，修复后只复核 FAIL 项，仍不通过即汇总 FAIL 清单升级用户，不进第 2、3 轮。本口径全局唯一，各赛道规则**不得另设计数器** |
| **单一产物源** | 交付材料用脚本同步，**不手工镜像多份**。禁止重复实现同一模块；独立复算须有理由并写入状态记录，产物放**独立目录**，不回灌主源 |
| **重产物只在终稿渲染** | 中间轮次**不得**生成完整 DOCX/PDF；终稿一次渲染 + 一次校验 |

## 三、轮次闸门（机械执行，不靠自律）

审查轮次封顶由 `scripts/round_gate.py` 机械保证：账本**只由脚本追加**，
轮次计数与状态记录行**都由脚本产出，模型不手写**。两道硬前置：

1. **无未修 FAIL 项不得开轮**——把"复核到 PASS"这个无不动点的循环改成单调递减过程
2. **上一轮不闭合不得开下一轮**

触顶后 `begin` 拒绝执行，只能 `signoff` 显式放行（须留放行人 + 理由），或按规则升级用户。
命令与退出码见脚本 docstring。

> **注：机械保证只覆盖轮次闸门，不覆盖秘书门禁。** 父项目曾有一个 `enforce_secretary` PreToolUse hook
> 试图强制 §零 阶段 0，2026-09-20 核查为**死代码**：hook 用了被弃用的 `{"script": ...}` 形状、脚本用 legacy
> `{"allow": ...}` 协议、门禁文件 `.claude/.secretary_gate.json` **从未存在过**。该 hook 与脚本已随规则层
> 合并一并移除。**§零 的秘书分解靠文本自律，不要以为有 hook 兜底。**

## 四、环节 token 归因

每环节收尾记一个**估算** token 值（归因用，不触发额外计算）。
单环节超 `scripts/context_monitor.py` 的 `STAGE_BUDGET_TOKENS`（默认 80k）时标出，并压缩该步输出。

> **此为估算口径，不是精确计量**——用于自律与事后归因，不得声称是实测值。

## 五、子 Agent 工具分档

> **本节的数字是实测值**（2026-09-20）。测法：`claude -p` 探针派生目标 Agent，读
> `<session>/subagents/*.jsonl` **首条 assistant 记录**的 `input_tokens`（该轮 cache_read=0，即全额底盘）。
> 历史量级另由 125 份子 Agent transcript + 39 个会话 transcript 全量解析得出，零额外 API 花费。

**底盘不是一次性成本，而是每轮重读。** 实测：固定底盘 × 轮数 占子 Agent 输入总量的 **48.9%**
（general-purpose 档 51.6%）。而底盘本身**一次性**的占比极小——规划期全部子 Agent 的底盘合计
仅占该阶段成本的 **0.66%**。故：**按「少派几个 Agent」省底盘方向是错的，按「每轮底盘更小」省才对。**

### 硬约束

1. **派生 Agent 必须选能完成任务的最省档**：默认 `ra-build`，纯只读默认 `ra-scan`，
   产出文本为主用 `ra-write`。`general-purpose` / `claude` **仅当**任务需要联网检索、
   MCP（MATLAB / officecli）或嵌套派生时才用，且须在派发说明中写明理由。
2. **禁止为「省底盘」而减少 Agent 数量或砍并行探查**——方向反了（见上）。
   要砍的是每轮上下文：子 Agent 只报结论 + `path:line`，**禁止回贴大段文件内容 / 完整日志 / 完整代码**。
3. **长寿命 Agent 比换新 Agent 贵**：实测每轮上下文随轮数增长（≤60 轮档 ≈ 68k/轮，
   250 轮以上档 ≈ 111k/轮），是底盘的 2–3 倍。**超 ~100 轮应交接给新 Agent**（交接摘要，不交接全文）。
4. `tools:` 前端是**唯一**能裁掉第二梯队工具 schema（Workflow / Cron / Monitor / DesignSync / MCP 等）
   的通道——`settings.json` 没有任何按键可按工具名移除 schema。

> **多 Agent 的真实成本倍率**：实测同一会话内「子 Agent 支出 / 主链支出」= **中位 0.56×**
> （17 个会话，范围 0.02×–3.69×）。**"多 Agent ≈ 15× token"未被实测支持**——但这不等于多 Agent 便宜：
> 其成本体现在**轮数 × 每轮上下文**，而非底盘。分级判据见 §零。
